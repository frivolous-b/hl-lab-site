Validation Gate — design

Phase 1, step 1 of ROADMAP.md. Written 2026-09-26; owner decisions recorded the same day (section 6). Step 2 (section 5) implements it, starting with the signal interface and event engine.

The gate is the single path from "signal idea" to "eligible for paper trading". It must (a) accept any kind of signal source without a new harness each time, (b) return one of PASS / FAIL / INSUFFICIENT_DATA under rules fixed before any new data is looked at, and (c) reproduce every negative result the lab already has (section 4) before it grades anything new.

1. Problem

Two incompatible signal paths exist today.

Candle path Event path
Entry point backtest.engine.run_backtest(df, strategy) strategies.wallet_mirror.simulate_mirror_trade(signal, …) / strategies.wallet_bracket.simulate_bracket_trade(signal, …)
Signal shape Strategy.on_bar(bars, position) -> {-1,0,+1} called every bar: a target position one dict {coin, side, entry_ts, exit_ts}: one trade per external event
Positions one net position per run; flip = close + open on the same bar each signal is an independent trade; overlaps allowed
Fills next bar open, cost model moves the fill price (CandleEstimatedCostModel, lagged volatility) next bar strictly after the event, raw open; slippage + fee deducted as flat bps × notional
Exits only when the strategy changes target mirror: next bar after the wallet's exit; bracket: intrabar TP/SL, SL first if a bar spans both, fallback to the wallet exit
Funding lookup_funding_rate once per bar, mark-to-market notional every funding event in (entry_fill, exit_fill], fixed notional
Output BacktestResult, graded by validation/criteria.py per-trade dicts, graded by a one-off aggregate binomial in the runner script

Consequences:

  • Every new signal source has needed its own runner and its own grading code. Wallet-following, funding harvest (pair engine in examples/run_funding_neutral_*.py) and the Project 3 congruence diagnostic each re-implemented part of the pipeline.
  • Results from the two paths are not comparable. The paths differ in slippage, funding accrual and exit timing, not only in signal logic.
  • The event path never went through criteria.py. Its verdicts came from ad-hoc tests in the runners.

2. Universal signal interface (proposal)

2.1 Event schema

@dataclass(frozen=True)
class SignalEvent:
    ts: pd.Timestamp        # UTC; see timing rule below
    asset: str              # HL coin symbol, e.g. "ETH"
    side: Side              # LONG | SHORT | FLAT
    strength: float = 1.0   # 0..1; sizing = base_notional * strength
    source_id: str = ""     # "<source>@<version>", e.g. "rsi14_4h@v1"
    meta: dict = field(default_factory=dict)  # free-form; reserved keys below

Reserved meta keys: ticket_id (ticket position mode, 2.3), exit_hint_ts (a known future exit, used by the wallet source), bracket (per-event override of TP/SL ROE and leverage).

Timing rule (the no-lookahead invariant, one rule for all sources). ts lies inside the bar during which the information became available. The executor fills at the open of the first bar whose timestamp is strictly greater than ts. For external events, ts is the event time. For candle strategies, it is the decision bar's timestamp (HL candles are labelled by open time, and the decision is made at that bar's close). Both cases give "fill at the open of the next bar", which is what both current paths do: the engine through pending_target, the wallet path through searchsorted(side="right").

strength is 1.0 for every existing source. The step-2 gate ignores it beyond sizing.

2.2 Adapters

CandleStrategyAdapter(strategy) wraps any Strategy without modification. The executor drives it bar by bar and calls strategy.on_bar(df.iloc[:i+1], position) with the actual position. When the returned target differs from the actual position, the adapter emits one event: +1 → LONG, -1 → SHORT, 0 → FLAT, with ts = bar.timestamp.

  • The strategy is pulled with position feedback. Its events are not pre-generated, because on_bar reads position: the same bars can give different targets depending on what is held. Pre-generating would silently change behaviour once a bracket or max-hold exit (2.3) moves the position underneath the strategy.
  • Emitting on "target ≠ actual position" is exactly the engine's pending_target / _execute_fill no-op rule. With brackets and max hold off, the event stream and the fills are identical to run_backtest.
  • This covers the six candle strategies: bollinger, ma_crossover, rsi, donchian_breakout, funding_harvest and funding_harvest_neutral. The first five map directly to one directional leg. FundingHarvestNeutral returns +1 to mean "pair open" (short perp + long spot). That is a two-leg position, which a single-asset event cannot express. In step 2 it keeps running through its existing pair simulator (run_pair_backtest + backtest/basis_pnl.py) and reaches the gate through the same trade-record interface (2.5). A multi-leg event (meta["legs"]) is deferred until a Phase 2 hypothesis needs it.

EventSignalSource takes an external stream (wallet fills, funding-threshold crossings, listings, …) and yields SignalEvents directly. It never sees future events: the executor consumes them in ts order. Built-in constructor for the existing data: EventSignalSource.from_round_trips(signals) turns each wallet round-trip {coin, side, entry_ts, exit_ts} into an entry event at entry_ts and a FLAT event at exit_ts, sharing one ticket_id.

2.3 Execution model

One executor, backtest/event_engine.py, consumes events for one asset's candle series:

  • Entry: open of the next bar (timing rule 2.1).
  • Exits, whichever comes first:
  • (a) an opposite-side or FLAT event, filled at the next bar's open. An opposite-side event in net mode is a flip (close and open on the same bar, one round-trip, as the engine does now);
  • (b) an ROE bracket (default tp_roe=0.12, sl_roe=0.08, leverage=3, the values in STRAT-BC position_manager.py), walked on the bars after the entry bar, SL first if one bar spans both levels, filled at the level price;
  • (c) max_hold_bars, filled at the open of the bar after the limit.

(b) and (c) are off unless configured. - Costs: a CostPolicy, either - model_fill: backtest/cost_model.py fill() moves the fill price (current engine); or - flat_bps: raw open fill, slippage + fee deducted as bps × notional per leg (current wallet path). - Funding: a FundingPolicy, one of - per_bar_lookup_mark: the current engine; one rate per bar at close, mark notional; - per_event_fixed_notional: the current wallet path; - per_event_mark: backtest/funding_pnl.accrue_funding_for_position, every settlement in (entry, exit] at mark notional. - Position mode: - net: one position per (source_id, asset), as the engine does; - ticket: each entry opens its own position, closed by the FLAT event with the same ticket_id or by (b)/(c); overlapping tickets are allowed, as the wallet path does. - End of data: - mark_to_market: an open position stays unrealized and is in equity but not in the round-trip count, as the engine does; - skip_ticket: a ticket without an exit bar is skipped with a reason, as the wallet path does.

The executor returns a BacktestResult-compatible object, so criteria.evaluate_window grades it unchanged, plus a list of TradeRecords for the pooled level (2.5).

2.4 Regression requirement: reproducing both paths exactly

The old paths stay in place until parity is proven. Each path maps onto a fixed configuration of the executor:

Current path Source Config
run_backtest(df, S, cost_model=M, funding_df=F) CandleStrategyAdapter(S) net, model_fill(M), per_bar_lookup_mark(F), no bracket, no max hold, mark_to_market
simulate_mirror_trade(sig, …) from_round_trips([sig]) ticket, flat_bps(slip, fee), per_event_fixed_notional, no bracket, skip_ticket
simulate_bracket_trade(sig, …) from_round_trips([sig]) as mirror + bracket(tp, sl, lev) with fallback = the ticket's FLAT event

Details that must be copied exactly, not "improved", during step 2:

  1. Engine funding charges one rate per bar: the latest settlement at or before the bar's open-time label. It charges at bar close, on the entry bar, and not on the exit bar.
  2. Engine fees are charged on notional for both legs, not on exit value. units = notional / entry_fill_px, with the fill price already slipped.
  3. Engine flip is recorded as one kind="flip" trade and counts as one round-trip.
  4. Bracket levels are computed from the entry fill price (the raw open in flat_bps mode). The walk starts at entry_idx + 1 and includes the fallback bar itself.
  5. Wallet funding sums every event in (entry_fill_ts, exit_fill_ts] × fixed notional, and rounds the result dict to 6 dp.

Parity test (step 2b):

  • Every examples/ result that feeds FINDINGS and is reproducible from cache is re-run through the executor.
  • Per-trade fields (timestamps, fill prices, realized P&L, funding) match to 1e-9 relative.
  • Per-window evaluate_window outputs and evaluate_overall verdicts are identical.
  • The wallet check uses the recorded results/walletfollow_stage3_{mirror,bracket}_trades.csv as golden files: 45 signals each, 37 backtested and 8 skipped (no HL candles). Both the P&L and the skip reasons must match.

Legacy quirks found while writing this (replicated during step 2, fixed only afterwards as separate commits with a before/after results delta):

  • 4h/1d funding undercount — FIXED (2026-09-26). The engines charged one hourly HL rate per bar: 1 of 4 settlements on 4h bars, 1 of 24 on 1d. Both engines now accrue every hourly settlement inside the bar (backtest.funding_pnl.accrue_bar_funding), at the bar-close mark notional, with no resampling of the funding series. 1h results are byte-identical to before (verified on all six candle strategies × BTC/ETH). The ETH/RSI 4h funding line moved from −$147.70 to −$576.50 (earned); its verdict did not change. A slot with no usable record is skipped and counted in BacktestResult.funding_records_missing (one warning per run).
  • Bracket fallback bar. The walk checks the fallback bar's high/low even though the fallback exit fills at that bar's open, so a TP/SL later in that bar can override an exit that should already have happened.

2.5 What the gate consumes

The gate never sees events. It sees, per walk-forward window, a train result and a test result (each BacktestResult-compatible), plus the test window's TradeRecords:

TradeRecord(source_id, asset, window, entry_ts, exit_ts, side,
            net_pnl_usd, net_return_pct, funding_usd, regime_at_entry)

Anything that can produce these can be graded: the event executor, the funding pair simulator, or a future live-shadow replay. For parameter-free sources (wallet streams) there is nothing to fit. "Train" is simply the source run over the train slice, which gives evaluate_window the train win rate its decay check needs.

The same SignalEvent is the return type of the generate_candidates hook that MERGE_INVENTORY §C-ENG proposes for the ported STRAT-BC engine, so one strategy object serves both backtest and paper trading.

3. Gate specification

Final verdict ∈ {PASS, FAIL, INSUFFICIENT_DATA}.

Statistic conventions:

  • Binomial tests are one-sided, as validation/significance.py already does. FINDINGS quotes some two-sided figures (ETH/RSI p = 0.229 two-sided = 0.114 one-sided); the gate records the one-sided value.
  • α = P_VALUE_THRESHOLD = 0.10. FAIL rules use α unadjusted (they never promote anything). The PASS rule uses the Bonferroni-adjusted α_i = 0.10 / m across the ledger (3.4, 3.6).

Test families (decision 1). Each hypothesis is registered with exactly one test family, and the family cannot change afterwards:

family for statistic behind p_up / p_down
binomial mean-reversion-type signals (edge = win rate) exact one-sided binomial on wins vs 50 %
mean_return trend-type signals (edge = payoff asymmetry; win rates of 24-39 % by design) one-sided bootstrap on the mean per-trade net return: resample the trades with replacement (B = 10,000, fixed seed) after centring them on 0; p_up = share of resampled means ≥ the observed mean, p_down = share ≤ it
daily_returns (added 2026-09-27, H8; section 3.7) exposure / allocation rules without discrete trades (edge = risk-adjusted return over a benchmark) circular block bootstrap (B = 10,000, block 20 days, fixed seed) of the paired daily strategy and benchmark returns on the difference of annualised Sharpe, strategy − benchmark, centred on 0; p_up = share of centred resampled differences ≥ the observed one, p_down = share ≤ it

The family applies at both levels (daily_returns has its own two levels, section 3.7). At Level 1 it replaces the binomial p criterion inside evaluate_window for mean_return hypotheses. Implemented in validation/criteria.py (evaluate_window_mean_return) and validation/gate.py.

3.1 Level 1: per-window

This is the existing validation/criteria.py, unchanged:

  • per window: PF ≥ 1.15, net return > 0, binomial p < α, win-rate decay ≤ 20 %, ≥ MIN_TRADES_PER_WINDOW (5) trades and a finite PF;
  • overall: evaluate_overall.

Mapping to L1:

evaluate_overall verdict L1
VALIDATED EDGE PASS
WEAK CANDIDATE / REJECTED FAIL
INSUFFICIENT_DATA INSUFFICIENT

Window length scales with bar size (added 2026-09-26, H1b). The per-window level only grades windows with at least MIN_TRADES_PER_WINDOW (5) trades, and that constant does not change. What changes with the timeframe is how much calendar time a rule needs to produce 5 trades. The registered test-window lengths are:

bar size test window reference
1h 30 days Stage 4.1 / 5 (60 d train, 30 d test)
4h 30 days ETH/RSI 4h full history
1d 365 days H1b onward; H1 used 90 days and every one of its 45 windows was below 5 trades

A hypothesis registers its window length with its cells, before it runs; changing it afterwards is a new registration. Windows are non-overlapping, tiled backwards from the holdout cut.

3.2 Level 2: pooled

Level 2 pools all closed OOS test-window trades across windows (n trades, w wins). Positions still open at a window's end are not round-trips; they stay in that window's return only (legacy behaviour). It uses three statistics:

  • p_up: edge direction (binomial P(X ≥ w | n, 0.5), or the bootstrap equivalent, depending on the family);
  • p_down: adverse direction (binomial P(X ≤ w | n, 0.5), or the bootstrap equivalent);
  • pooled PF = Σ winning net P&L / |Σ losing net P&L|, and the pooled net P&L.

Rules, applied in order:

  1. n < N_FAIL_FLOOR (20) → INSUFFICIENT
  2. p_down < α → FAIL (significantly worse than a coin flip)
  3. pooled net P&L ≤ 0 or pooled PF < 1.0 → FAIL (loses money in aggregate)
  4. p_up < α_i (Bonferroni across the ledger) and pooled PF ≥ MIN_TEST_PF (1.15) → PASS
  5. otherwise (positive but not significant): n ≥ N_MIN_POOLED → FAIL (adequately powered, no edge); else → INSUFFICIENT

Rules 2-3 make FAIL asymmetric on purpose. Power is needed to claim "no edge despite a positive estimate". It is not needed to stop promoting a strategy whose own sample points the wrong way. Without them ETH/RSI 4h (56 trades, below N_MIN_POOLED) could only ever be INSUFFICIENT_DATA, never the FAIL its record supports.

3.3 Combining levels

L1 \ L2 PASS FAIL INSUFFICIENT
PASS PASS FAIL INSUFFICIENT_DATA
FAIL FAIL FAIL FAIL
INSUFFICIENT INSUFFICIENT_DATA ¹ FAIL INSUFFICIENT_DATA
  • PASS requires both levels.
  • Per-window INSUFFICIENT can become FAIL through the pooled level, never PASS.
  • L1 FAIL is final: the windows had enough trades and did not replicate.

¹ Accepted deviation (decision 2). Elsewhere INSUFFICIENT_DATA is final only when pooled n < N_MIN_POOLED. This cell can have n ≥ N_MIN_POOLED: a significant pooled edge spread over windows too thin to test replication. It cannot be PASS, and FAIL would be wrong, so it is INSUFFICIENT_DATA with reason "re-window required". A longer test window must be registered as a new ledger row before the re-run, and the re-run counts as a new test toward m.

3.4 N_MIN_POOLED: power calculation

Setup: exact one-sided binomial vs 50 %, 80 % power, taking the smallest n from which power stays ≥ 80 % (the exact test's power is saw-toothed in n).

true win rate α = 0.10 α = 0.05 α = 0.02 (0.10 / 5) α = 0.01
55 % 484 654 866 1028
60 % 126 169 222 261
65 % 57 76 100 119

Power at the pooled sizes the lab has actually produced (α = 0.10):

n 55 % 60 % 65 %
30 0.14 0.29 0.51
60 0.26 0.56 0.83
100 0.38 0.76 0.96
150 0.44 0.86 0.99

Decision 3: N_MIN_POOLED = 130, which is 80 % power to detect a true 60 % win rate at α = 0.10. It is the data threshold: it only decides between FAIL and INSUFFICIENT for a positive but non-significant pooled result (rule 5). PASS is a separate requirement: p_up < α_i = 0.10 / m, where m counts every H* cell in the ledger (3.6). The two thresholds do different jobs, and N_MIN_POOLED is not re-derived when m grows. With m cells registered, a real 60 % edge needs roughly the α_i column of the table above to be likely to PASS (m = 5 → α_i = 0.02 → about 222 trades). Three consequences follow:

  • A 55 % edge is undetectable at the lab's current trade rates. It needs about 480 pooled trades (about 870 after a 5-way Bonferroni). The gate cannot distinguish a 55 % strategy from noise, and FINDINGS should say so, not imply otherwise.
  • After Bonferroni the n a strategy needs to pass grows with m (222 at α_i = 0.02), even though N_MIN_POOLED stays at 130. Between 130 and that number, a positive, non-significant result is a FAIL: the lab spent its data and found no edge strong enough to survive the correction. For the mean_return family the table does not apply (power depends on the return distribution); 130 is used as the same data threshold.
  • N_FAIL_FLOOR = 20 (4 × MIN_TRADES_PER_WINDOW) is a policy floor, not a power number. It stops rule 3 from closing a hypothesis on a handful of trades.

3.5 Regime scoping

Every verdict carries the regimes its OOS trades covered. It is never worded unconditionally: "no edge in {bull, range} over 2024-04-30 → 2026-05-30", not "no edge". A PASS is worded "edge in regime X", as H1 requires.

Fixed classifier (decision 5). It uses the 200-day SMA of the traded asset's daily closes plus its slope, computed at the daily bar close:

  • bull = close > SMA200 and SMA200 today > SMA200 20 daily bars earlier;
  • bear = close < SMA200 and SMA200 today < SMA200 20 daily bars earlier;
  • range = otherwise, including the first 219 days, before both SMA200 values exist.

A trade's regime is the label at the last completed daily close at or before its entry decision, so an intraday trade never sees its own day's close. SMA length (200) and slope lookback (20) are frozen; a change is a new classifier version and invalidates earlier regime labels.

Each TradeRecord stores regime_at_entry. The verdict reports n per regime. A regime with fewer than N_FAIL_FLOOR trades is listed as "not covered", with no claim either way.

3.6 Multiple-comparison ledger and holdout

docs/HYPOTHESIS_LEDGER.md holds H1-H6 as registered hypotheses. Each hypothesis's spec expands it into test cells before anything runs. The full row format, one row per test cell:

id registered hypothesis / cell family data range (train+test) holdout cut α_i status verdict p_up (pooled) notes
H1.BTC.1d 2026-10-xx bull-regime trend, BTC 1d P2 … … 0.10/m registered — — spec link
  • Row types:
  • H*: Phase 2 hypotheses, which count toward m;
  • CAL*: calibration runs of known negatives, which are recorded but do not count toward m, because no PASS is sought;
  • PRIOR*: the Stages 3-7 and Projects 2-3 tests, back-filled for the record.
  • Rows are append-only. A verdict is filled in once. A re-run is a new row that references the old one. The unpinned ETH/RSI re-run (FINDINGS, 2026-09-26) is back-filled as a PRIOR row.
  • Bonferroni over hypotheses gives PASS (method fix 2026-09-27, validation/gate.py): α_adj = 0.10 / m, where m = every hypothesis (rule set) registered in the ledger, run or not: the bare-id rows H1, H1b, H2a, H2b, H3 … (registered_hypothesis_count). m only grows. α_adj applies to a hypothesis's pooled cell. Per-coin cells of one hypothesis are sub-tests of the same rule set; they are controlled with Benjamini-Hochberg FDR at q = 0.10 over that hypothesis's per-coin p_up values (evaluate_hypothesis): sort the available p-values, largest k with p_(k) ≤ k/n · q, the k smallest are significant for rule 4. Cells below N_FAIL_FLOOR have no p and are never significant. FAIL rules use α = 0.10 unadjusted under both. Before the fix m counted cells (H1 had m = 11, H1b m = 31); the ledger records the re-grade of the one pooled cell that was ever graded under the old count (H1b.pooled: FAIL either way, p = 0.317).
  • Holdout: the last 90 days, locked. The cut date is written in the ledger header before any Phase 2 run. The data is snapshotted to the parquet cache that day, because HL retention is rolling. Holdout rows run once, only for cells that PASS on pre-holdout data, and the same gate is applied. A holdout FAIL is final.

3.7 The daily_returns family (added 2026-09-27, H8)

For rules whose output is an exposure path rather than discrete trades, the unit of evidence is a day, and the question is whether the rule beats holding the instrument. validation/gate.py: evaluate_daily_returns takes, over the same days, the strategy's and a benchmark's daily returns (equity_t / equity_{t−1} − 1, both after costs and funding) plus the strategy's daily exposure flag.

Metrics (both series): annualised return (geometric, 365-day year), Sharpe = daily mean / daily std × √365 with rf = 0, max drawdown of the cumulative equity, Calmar = annualised return / |max DD|, exposure = share of days with a position.

Statistic: the difference of Sharpe, strategy − benchmark. Circular block bootstrap of the paired days (block length 20, B = 10,000, seed 0), centred on 0 as for mean_return: p_up = share of centred resampled differences ≥ the observed difference, p_down = share ≤ it.

Levels and verdict:

  • Data threshold: fewer than 3 years (1,095 days) → INSUFFICIENT_DATA, nothing else is claimed.
  • Level 1, per calendar year (years with ≥ 60 days). v2, method correction of 2026-09-27, applied after seeing the H9c and H9d results (same category as the Phase 0 PF = inf fix: an instrument defect exposed by a result, corrected openly, every affected cell re-graded under both versions and both verdicts recorded):
  • a year's Sharpe is undefined when the strategy's daily-return standard deviation in that year is below MIN_DAILY_STD = 0.0005 (5 bps). A modelled-basis series (H9b-H9d: spot = perp mark) has almost no daily variance, so its yearly Sharpe is an artefact — a year that lost 0.6 % of capital showed a Sharpe of −3.5 and failed the v1 floor;
  • the floor for ALL daily_returns cells is now the calendar-year net return ≥ MIN_YEAR_RETURN = −2.0 % (registered constant; rationale: a carry or allocation strategy's "catastrophic year" is a capital loss, not a Sharpe artefact);
  • the v1 Sharpe-difference floor (≥ −0.5) remains an additional check ONLY for years whose daily std is ≥ MIN_DAILY_STD. Any graded year that breaches the applicable floor(s) → L1 FAIL. evaluate_daily_returns(..., version="v1") reproduces the v1 rule for the record. v1 (2026-09-27, H8 and H9c/H9d as first run): each graded year's Sharpe difference ≥ −0.5.
  • Level 2, whole sample, rules in order: (1) p_down < α = 0.10 → FAIL (the benchmark is significantly better); (2) strategy max DD not strictly smaller in magnitude than the benchmark's → FAIL — against a benchmark with no drawdown (cash) this relative condition is vacuous, so a hypothesis may register an absolute cap (max_dd_cap, H9: 10 %): rule 2 then passes iff (the benchmark has no drawdown, or the strategy's is strictly smaller) and the strategy's max DD is strictly below the cap; (3) p_up < α_adj (Bonferroni for a pooled cell, BH-FDR for per-coin cells, section 3.6) → PASS; (4) otherwise FAIL (≥ 3 years of data and no significant edge).
  • Verdict: PASS only if L1 and L2 both pass; FAIL otherwise.

Benchmark mode hodl_btc (added 2026-09-27, ROADMAP "North star"). DailyReturnsInput.hodl_btc(...) / hodl_btc_days(...): the strategy's daily returns are computed in BTC units, equity_btc = equity_usd / BTC close of the same day, and the benchmark series is zero excess (HODL BTC = constant 1.0 BTC). Everything else in the family is unchanged: the Sharpe difference is the strategy's BTC-denominated Sharpe against 0, the per-year floor is the BTC-denominated calendar-year return ≥ −2 % (Sharpe floor only where the year's daily std ≥ 5 bps), ≥ 3 years, block bootstrap, Bonferroni / BH. The benchmark has no drawdown in BTC units, so the relative max-DD rule is vacuous in this mode exactly as against cash; a hypothesis may register an absolute cap (max_dd_cap), otherwise the BTC-denominated max DD is reported and not graded.

Verdicts are regime-scoped like every other family (3.5); a regime-only exposure rule is by construction "long in bull", so its scope statement is the benchmark comparison over the whole sample.

7. Strategy-loop level 2 (added 2026-11-05, owner decision)

Gate change, recorded openly. The strategy loop (lab/loop.py, DISCOVERY_LEDGER.md) discovers on 2023-05-12 → 2025-06-30 and confirms on 2025-07-01 → 2026-06-28: the only data its level 1 never saw, one year. Section 3.7 needs 3 years (MIN_DAYS_DAILY = 1,095) before it grades anything, so a loop confirmation under 3.7 could only ever be INSUFFICIENT_DATA (batch 2026-45, H14). This section adds a level-2 rule for loop ideas. It does not change sections 3.1-3.7, which still grade every hypothesis registered in the ledger.

Rule (lab/level2.py, constants frozen). On the level-2 window, with the idea's daily series in its numeraire (USD against cash for a market-neutral idea, BTC units against HODL BTC for a directional one), the idea PASSes only if all five hold:

  1. its total return over the window is greater than the benchmark's;
  2. p_up ≤ 0.10, one-sided, on the daily_returns v2 statistic (3.7: circular block bootstrap of the Sharpe difference, block 20 days, B = 10,000, seed 0). α = 0.10 is not adjusted (owner decision);
  3. no calendar quarter with at least 30 days in the window has a net return below −2 %;
  4. its max drawdown is strictly within the 10 % cap (|max DD| < 10 %), in its numeraire;
  5. it has at least ceil(min_trades × 362 / 781) round trips: the idea's level-1 minimum scaled by the calendar lengths of the two windows (level 2: 362 days, level 1: 781 days; 20 → 10).

Otherwise FAIL.

Recording. Level 2 is registered (before the run) and recorded (after it) in DISCOVERY_LEDGER.md only. A level-2 PASS is a paper-run candidate. It is appended to HYPOTHESIS_LEDGER.md, and so raises m, only when the owner approves its paper run; the paper run is its out-of-sample test. A candidate that matches the rejected list of IDEA_INTAKE.md also needs an override row there first (intake rule 4).

H14. The loop's first survivor was registered as H14 under the earlier design and graded INSUFFICIENT_DATA under 3.7. It is superseded: moved to discovery as D-2026-45-03 and re-run under this rule. H14 still counts toward m (m only grows).
